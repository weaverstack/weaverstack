Fabric Engineering Guides

One Dependency Graph Across 50 Microsoft Fabric Workspaces

How independently owned Fabric workspaces, each with its own catalogue, can assess the impact of a failure and recover from it across the whole organisation, without a central orchestrator.

Introduction

Many organisations adopt Microsoft Fabric as a self-service platform for the whole enterprise, not as a tool for one engineering team. A central team lands and conforms shared data, and dozens of business areas build on it in workspaces of their own, each with its own people, release cycle and priorities.

That arrangement works until something upstream breaks. When a central Bronze table fails, every team downstream needs the same two answers: what is affected, and how do we recover? In most estates nobody can answer either question for the whole organisation, because each team's pipelines, schedules and run history live with that team.

This guide shows that Fabric already holds what is needed to answer both, and tests it on 50 real workspaces. One failed Bronze table was traced to every affected object in the 49 other workspaces in under a minute and a half. The central team repaired its own estate without touching anyone else's. A business team saw and repaired its own share independently.

1. The enterprise problem

A typical federated estate looks like this:

  • A central team owns the Bronze Lakehouse in one workspace.
  • Another team owns the Silver Lakehouse and Gold Warehouse in a second.
  • Shared semantic models live in a third.
  • Forty or fifty business areas own workspaces of their own. They read central data and occasionally one another's.

Two common answers to cross-team failures both fall short. A central orchestrator that runs every team's pipelines gives one view of the estate, but it makes one team the gatekeeper for everyone's releases, which is exactly what self-service was meant to avoid. Independent schedules keep teams autonomous, but each team sees only its own runs: a business table can load successfully from stale or broken upstream data and report green.

What an enterprise needs is both at once. Every team should operate on its own, and the organisation should still be able to see its dependencies, assess the impact of a failure and coordinate recovery when it has to.

2. What Fabric already provides

Two properties of Fabric make an organisation-wide dependency graph possible without moving any data or adding a central service.

2.1 Every object has a five-part name

Every table, view and folder in Fabric can be named uniquely, across the whole tenant, with five parts. Semantic models and reports need the first three.

A name like this identifies an object without reference to any team's tooling. Two teams that have never coordinated can still talk unambiguously about the same table.

2.2 OneLake shares data across workspaces

Every Fabric tenant comes with a single OneLake instance (Microsoft 2026a). Its shortcuts let an item in one workspace read data held by an item in another, including a Lakehouse reading a Warehouse, without copying it (Microsoft 2026b).

In this experiment, Spark addressed tables in other workspaces directly by four-part name. A Warehouse's T-SQL reached only items in its own workspace, so each business team brought central Gold tables into its workspace through shortcuts in a small bridge Lakehouse and read them through that Lakehouse's SQL analytics endpoint.

The data is therefore already shared, and every object already has a name. What is missing is the information that connects them.

3. The two missing pieces

An organisation-wide dependency graph needs only two things beyond what Fabric provides.

3.1 Dependencies between five-part names

Each object's upstream must be recorded as the five-part names it reads. Within a workspace this is ordinary lineage. Across workspaces it is the shortcut: a shortcut names the item and path it reads, and the item's Fabric ID identifies the workspace and team that own it. Matching that ID against another team's records connects the two graphs, with nothing declared for the join.

3.2 Operational status of five-part names

Each object must also record its operational state: when it last loaded, whether that load succeeded, and when its upstream last changed. With that, a failed table can be traced to every object that read it, and an object that loaded successfully before its upstream was repaired can be identified as behind.

Neither piece needs a central store. If each team records both for its own objects, any team can read the records of the teams it depends on and assemble the part of the graph it cares about, or the whole organisation's.

3.3 Concurrency

Once the graph exists, loading across it is a scheduling problem. Independent branches in different workspaces should run together, while each reader waits only for its own upstream, including the SQL analytics endpoint refresh or OneLake publication between them. The techniques are the same as within one estate, described in Performance Engineering on Microsoft Fabric.

4. Experimental setup

The experiment built 50 real Fabric workspaces on an FTL64 trial capacity. Each workspace had its own catalogue, its own project and its own configuration. Every team was initialised, built and loaded independently before the experiment began.

Two business teams were deliberately made to read each other's summaries, forming a dependency cycle across workspaces. In a federated estate such cycles are inevitable, so the system has to tolerate them.

The experiment then introduced a failure into the central Bronze table BRZ.Customer, and tested what each team could see and do.

The tables are deliberately small. The experiment tests coordination across workspaces, not data volume; volume is the subject of the performance guide.

5. The implementation: Weaver

Weaver is an open-source data engineering framework for Microsoft Fabric. Every Weaver project keeps a catalogue in a Fabric Warehouse, and building and loading record both missing pieces there as a by-product: the dependencies between five-part names, including shortcuts into other workspaces, and each object's operational status.

5.1 The Weaver CLI

Every Weaver command works on one team's catalogue by default. Passing more than one catalogue joins them into one graph. There is no federation configuration: the catalogues already hold the dependencies.

# Health across the whole organisation
weaver health --catalogue SPREAD_BRONZE/Warehouse/Catalogue \
              --catalogue SPREAD_CENTRAL/Warehouse/Catalogue \
              ...         # every catalogue to include

# Team 05 reloads only what is behind, reading its upstream for context
weaver load --stale --catalogue SPREAD_TEAM_05/Warehouse/Catalogue \
                    --catalogue SPREAD_BRONZE/Warehouse/Catalogue \
                    --catalogue SPREAD_CENTRAL/Warehouse/Catalogue

Health assesses each catalogue in turn, with ancestry reaching through the others, and names the upstream cause of every finding. A load across several catalogues is one run: one graph, one workflow ID, each object recorded in its own team's catalogue. --stale selects only the objects that are behind their upstream. A team needs read access to the catalogues it joins, and a load that changes another team's objects needs that team's permission.

5.2 The Catalogue Dashboard

The Catalogue Dashboard presents the same joined graph in Power BI. It reads up to ten catalogues over Direct Lake, or any number imported, and only reads them. Its Workspaces page shows the network of teams; Health, Orchestration and the Entity dictionary narrow to the items chosen. The Filters pane narrows the data by workspace, item and object before a page is built, and the whole Dashboard can be exported as static HTML that opens without a running capacity.

6.1 Impact across the organisation

One Health operation across all 50 catalogues found the failed table and the 77 objects downstream of it in 45 other catalogues: 61 Warehouse tables, 5 Lakehouse tables and 11 semantic models. Only one object had failed. The other 77 were still serving their last good load, and each finding named BRZ.Customer as its cause. The four thin-report teams have nothing to load and stayed green.

6.2 Independent recovery

The central team repaired its estate with one load --stale over its own three catalogues. The plan held six objects to reload, ordered across Bronze, Silver/Gold and the central semantic model, with the SQL endpoint refreshes and OneLake publications between them. No business team's data was reloaded.

Team 05 then saw, from its own catalogue alongside its upstream, that its tables were now behind the repaired data rather than broken. It reloaded only its two stale tables and returned to green, without waiting for the central team or asking it to run anything.

6.3 Cycles

The cycle between teams 01 and 02 was found and reported once. Loads ordered it by cutting one edge, and the rest of the estate ran normally. One object stayed correctly behind afterwards, because it read the other team's previous load. A system that reports this honestly is more useful than one that declares everything green.

6.4 Coordination when required

The same commands work across the whole organisation when coordination is wanted. One federated load across all 50 workspaces ran 125 nodes in one graph: 80 objects to load, and 45 SQL endpoint refreshes and OneLake publications that make sure each team reads fresh data. It finished in just over five minutes, of which execution took about two, with up to 12 nodes running at once. The rest was reading 50 catalogues, planning and starting Spark.

After the failure, one organisation-wide load --stale reloaded only the 71 objects still behind and brought every workspace back to green, except the object held behind by the cycle.

7. Conclusion

Fabric gives every object a tenant-wide name and lets workspaces share data through OneLake. With each object's dependencies and operational status recorded beside it, those properties are enough for 50 independently owned workspaces to behave as one dependency graph when the organisation needs one.

That makes two modes possible on the same platform:

  1. Decentralised by default.Every team builds, loads, tests and checks its own estate independently, with its own catalogue and release cycle.
  2. Coordinated when required.Any team, or the organisation, can join the relevant catalogues to see dependencies, assess impact and coordinate recovery across workspaces.
