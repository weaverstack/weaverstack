Choosing dbt for Microsoft Fabric

A practical look at where dbt fits on Fabric, its limitations and missed opportunities.

Matthias Wong · 3 November 2026

Are you considering dbt for Microsoft Fabric, or already using it? A question worth asking is whether it covers the whole of what you'll build on Fabric.

dbt brought real engineering discipline to SQL development: dependency management, testing, documentation and repeatable deployments. If your Fabric work is mostly SQL transformations in a Warehouse, dbt may be all you need.

Fabric is broader than that. Python, Spark, Lakehouse, Warehouse, OneLake and Power BI share one platform, and as a project uses more of it, the places where dbt stops start to matter.

A typical project grows piece by piece. A Python notebook for ingestion. A Spark job for Lakehouse processing. A dbt project for the Fabric Warehouse. Fabric pipelines to connect them. Separate arrangements for deployment, testing and monitoring. Each addition is reasonable on its own. But they add up, and at some point you start to wonder: are we designing our data engineering around what Fabric makes possible, or around what our framework was designed to support?

This article walks through five places where those pieces meet, and the questions worth asking about each before you commit.

The first seam: a table is a table, in Python, Spark SQL or T-SQL

A production table needs the same things whether Python, Spark SQL or T-SQL populates it: staging, primary keys, change detection, merging, auditing, and the ability to resume safely after a failure. These aren't SQL features. They're data engineering requirements.

Fabric lets you pick the right engine for each job. Python for acquisition and awkward file formats. T-SQL for relational modelling. Spark SQL for scale.

dbt gives SQL models that discipline. Tables loaded by Python sit outside it, so the engineering standard often changes when the language does: different development patterns, different execution, different conventions, and often a home-grown framework to fill the gap.

A primary key doesn't stop being a primary key because you wrote it in Python. So why should choosing Python mean stepping outside your engineering framework? And why should a data team have to invent another one to fill the gap? The programming language changes how a table is implemented. It doesn't change the standard the table is held to.

The second seam: orchestrating jobs, not data, across Lakehouse and Warehouse

A typical Fabric architecture: a notebook populates Delta tables, a dbt job transforms them, another job builds the final models, and a pipeline connects the stages. Microsoft documents patterns like this, and they work.

dbt understands the dependencies between its own models, and handles them well. It doesn't see the Python that feeds them or the Lakehouse processing beside them, so the orchestration that spans them sits in a layer above, scheduling notebooks and jobs.

Now suppose one source changes, affecting two Delta tables and three Warehouse tables. The real dependencies are between those five objects. So why are we scheduling, rerunning and monitoring the notebooks and jobs that contain them? As the estate grows, those job boundaries start to decide how failures, concurrency and reruns are handled.

Why should the boundary between Lakehouse and Warehouse set the boundary of the engineering framework? Fabric brings them together. The dependency graph should too.

The third seam: keeping track of incremental loads

Running a warehouse in production is more than executing transformations.

Suppose a source delivers 100,000 records and only five have changed. The warehouse should know that. It should update those five, leave the rest untouched, and record exactly what happened.

Now suppose 40,000 records vanish overnight. Were they deleted, or did the extract break?

Or the load fails halfway. Where should the next run start?

These are basic warehouse disciplines: detecting genuine change, handling deletes deliberately, keeping change timestamps that mean something, and advancing bookmarks only when a load succeeds.

dbt executes transformations, and does it well. Incremental models cover part of this, one model at a time, but dbt doesn't keep track of what changed row by row, or where each table is up to. So teams build their own bookkeeping around dbt. Then again for Python. And again for the Lakehouse.

Why should keeping track of a data warehouse be a do-it-yourself project through customisation?

The fourth seam: OneLake changes how you can develop

OneLake is one of my favourite things about Fabric.

Some of my government sources take hours to acquire. With OneLake shortcuts, development can reuse that source data without copying or downloading it again. Change a transformation, rebuild the affected objects, inspect, repeat. Dozens of iterations in the time one acquisition would take.

But shortcuts alone don't give you that workflow. The framework has to know which data is borrowed, which objects it manages locally, and how to deploy changes safely.

Does the engineering framework take advantage of the innovation Microsoft has put into Fabric, or does it limit how much of it the team can adopt?

The fifth seam: who understands the whole Fabric estate?

By now there are many moving parts: notebooks, Lakehouse tables, Warehouse models, pipelines, separate execution histories, tests and deployment configurations.

When something breaks, where does the team look? Which object failed? What sits downstream of it? What actually changed? Which tests are now stale? Can just the affected work be rerun?

dbt has lineage and test results. Fabric has monitoring. A shared Git repository and a master pipeline help. Each shows part of the picture.

This matters more as AI agents take on development work. An agent learns through a tight loop: make a change, run it, read the result, fix it. From a command line, that loop takes seconds.

Split a pipeline across notebooks and dbt, and the loop breaks at every seam. The dbt half runs from a terminal. The notebook half runs somewhere else, with its results somewhere else again. The agent can change the code, but it struggles to see what its change did. Why should an agent need to learn ten systems to manage one pipeline?

The seams start as little inconveniences. As complexity grows, they become the architecture.

What to look for in a Fabric data engineering framework

What if we designed data engineering around Fabric, rather than fitting Fabric around a SQL framework? Whether you use dbt on its own, build around it, or choose something else, these are the capabilities worth checking against the work you'll do on Fabric:

  • One standard for every table, whichever engine populates it.
  • Dependencies between objects, not jobs, crossing Lakehouse and Warehouse.
  • Loading, testing, auditing and recovery under one set of conventions.
  • Development that reuses data through OneLake rather than copying it.
  • One operational record of what was deployed, loaded and tested.

The question is less about dbt itself than about what a data engineering framework should be responsible for on a multi-engine platform.

Putting it into practice: one framework across Fabric

Weaver is an open-source data engineering framework designed around Fabric's native capabilities. Each seam above has a direct answer in it.

  • One standard for every table. Python, Spark SQL and Warehouse T-SQL objects share one load contract: staging, declared keys, change detection, explicit deletes, audit columns and data-quality safeguards. Write a Warehouse SELECT and Weaver creates the table and loading procedure around it.
  • One dependency graph across Fabric. Python files, Lakehouse Delta tables, Warehouse tables, semantic models and Reports sit in a single graph. A load runs in dependency order, with Spark and each Warehouse in their own concurrency lanes, and a failure blocks only the work that depends on it.
  • Incremental state built in. Each table keeps its own bookmark, which advances only when its load succeeds, and every run records the rows inserted, updated and deleted.
  • Development on existing data. Mirror sets up a development workspace over existing data through OneLake shortcuts and Warehouse views, and materialises only the objects you change.
  • One operational record. Deployments, loads and tests are recorded in Fabric Warehouse tables. Health shows what is failing or stale, and a Power BI dashboard covers the whole estate.
  • Native Power BI. Deploy PBIP and TMDL semantic models and Reports, apply shared rules, and unit test DAX measures against SQL results.

Build, load and test run from a command line on your desktop, or from a Fabric notebook after pip install weaverstack. The same commands give an AI agent the full loop of change, run, check and fix across the whole pipeline, without leaving the terminal.

We built Weaver after years of enterprise data warehousing on SQL Server. We didn't want to give up that engineering discipline, or run separate frameworks for different parts of Fabric.

The benefit isn't just fewer pipelines. It's using Fabric's full capability without solving the same engineering problems again and again. See all of Weaver's features.

Deciding whether dbt is enough

dbt on its own is likely a good fit when:

  • most of your work is SQL transformations in a Fabric Warehouse
  • ingestion is handled elsewhere and rarely changes
  • you already have a working dbt project and a team that knows it.

But if your work is spreading across engines, it's worth asking some harder questions.

How much effort goes into coordinating separate systems?

How often does the team adapt its engineering to fit the framework?

Which Fabric capabilities is the team avoiding because they're awkward to integrate?

There's no reason to abandon an architecture that works. The useful question is how much of your Fabric work dbt covers, and how much you'll build and run beside it.
