The limitations and missed opportunities of dbt on Microsoft Fabric

Is a SQL transformation framework holding us back from what Fabric makes possible?

Matthias Wong · 3 November 2026

Microsoft Fabric is a multi-engine platform. Python, Spark, Lakehouse, Warehouse, OneLake and Power BI, all in one place.

So why are so many of us building on it around a framework designed for SQL transformations?

And what if that framework is the very thing holding us back?

To be clear, dbt is excellent at what it does. It brought real engineering discipline to SQL development: dependency management, testing, documentation and repeatable deployments. If your Fabric project is mostly SQL transformations, dbt may be all you need.

But Fabric offers much more than SQL transformations. And as you start using it, the seams appear.

A Python notebook for ingestion. A Spark job for Lakehouse processing. A dbt project for the Warehouse. Fabric pipelines to stitch them together. Separate arrangements for deployment, testing and monitoring.

Each addition seems reasonable. Each inconvenience seems minor. But they add up, and at some point you start to wonder:

Are we designing our data engineering around what Fabric makes possible, or around what our framework was designed to support?

The first seam: a table is a table

A production table needs the same things whether Python, Spark SQL or T-SQL populates it: staging, primary keys, change detection, merging, auditing, and the ability to resume safely after a failure.

These aren't SQL features. They're data engineering requirements.

Fabric lets you pick the right engine for each job. Python for acquisition and awkward file formats. T-SQL for relational modelling. Spark SQL for scale.

Yet the moment you cross from one to another, the engineering standards tend to change with it. Different development patterns. Different execution. Different conventions. And often a home-grown framework to fill the gap around the Python.

A primary key doesn't stop being a primary key because you wrote it in Python. So why should choosing Python mean stepping outside your engineering framework? And why should you have to invent another one to fill the gap?

The language should be an implementation choice, not a change in engineering standards.

The second seam: orchestrating jobs, not data

A typical Fabric architecture: a notebook populates Delta tables, a dbt job transforms them, another job builds the final models, and a pipeline connects the stages. Microsoft documents patterns like this, and they work.

Now suppose one source changes, affecting two Delta tables and three Warehouse tables.

The real dependencies are between those five objects. So why are we scheduling, rerunning and monitoring notebooks and jobs?

dbt understands dependencies between its own models. It doesn't see the Python that feeds them or the Lakehouse processing beside them. So another orchestration layer goes on top, with its own boundaries to maintain. As the estate grows, those boundaries start deciding how you handle failures, concurrency and reruns.

Why should the boundary between Lakehouse and Warehouse set the boundary of your engineering framework? Fabric brings them together. Your dependency graph should too.

The third seam: keeping track of what's happening

Running a warehouse in production is more than executing transformations.

Suppose a source delivers 100,000 records and only five have changed. The warehouse should know that. It should update those five, leave the rest untouched, and record exactly what happened.

Now suppose 40,000 records vanish overnight. Were they deleted, or did the extract break?

Or the load fails halfway. Where should the next run start?

These are basic warehouse disciplines: detecting genuine change, handling deletes deliberately, keeping change timestamps that mean something, and advancing bookmarks only when a load succeeds.

dbt executes transformations, and does it well. But it doesn't keep track of what changed row by row, or where each table is up to. Incremental models approximate parts of this, one model at a time.

So teams build their own bookkeeping around dbt. Then again for Python. And again for Lakehouse.

Why should keeping track of your own warehouse be a do-it-yourself project?

Reliable loading should be an ordinary expectation, not a special achievement.

The fourth seam: OneLake changes how you can develop

OneLake is one of my favourite things about Fabric.

Some of my government sources take hours to acquire. With OneLake shortcuts, development can reuse that source data without copying or downloading it again. Change a transformation, rebuild the affected objects, inspect, repeat. Dozens of iterations in the time one acquisition would take.

But shortcuts alone don't give you that workflow. The framework has to know which data is borrowed, which objects it manages locally, and how to deploy changes safely.

So why shouldn't this be central to how we develop on Fabric, rather than something we engineer separately?

That's the difference between adapting an existing framework to a new platform and designing one around what the platform can do.

The fifth seam: who understands the whole estate?

By now there are many moving parts: notebooks, Lakehouse tables, Warehouse models, pipelines, separate execution histories, tests and deployment configurations.

When something breaks, where do you look? Which object failed? What sits downstream of it? What actually changed? Which tests are now stale? Can you rerun just the affected work?

dbt has lineage and test results. Fabric has monitoring. A shared Git repository and a master pipeline help. None of them add up to one operational picture.

This matters more as AI agents take on development work. An agent learns through a tight loop: make a change, run it, read the result, fix it. From a command line, that loop takes seconds.

Split a pipeline across notebooks and dbt, and the loop breaks at every seam. The dbt half runs from a terminal. The notebook half runs somewhere else, with its results somewhere else again. The agent can change the code, but it struggles to see what its change did.

Fabric needs agent tooling for the whole pipeline, not one engine at a time. Why should an agent need to learn ten systems to manage one pipeline?

The seams start as little inconveniences. As complexity grows, they become the architecture.

Start with Fabric instead

What if we designed data engineering around Fabric, rather than fitting Fabric around a SQL framework?

What if a table was a table, whichever engine populated it?

What if dependencies crossed Lakehouse and Warehouse naturally?

What if loading, testing, auditing and recovery followed one set of conventions?

And what if OneLake were part of how you develop, rather than an integration exercise?

This isn't about adding features to dbt. It's about rethinking what a data engineering framework is responsible for on a multi-engine platform.

Why we built Weaver

We came to Fabric with years of enterprise data warehousing and SQL Server experience. We liked how well its technologies fit together. We didn't want to give up the engineering discipline we'd built, or run separate frameworks for different parts of Fabric.

So we built Weaver: an open-source data engineering framework designed around Fabric's native capabilities.

Weaver manages Python acquisition, Lakehouse tables and Warehouse T-SQL with one dependency graph, consistent conventions, and integrated Build, Load, Test and monitoring. It also supports Power BI semantic models and reports.

An example is I ❤️ Gov, a public website bringing together Australian government data from a multitude of sources. Its pipeline spans hundreds of objects and tests, combining Python acquisition, Delta processing and T-SQL modelling, all orchestrated from a single Fabric notebook rather than hundreds of individual pipelines. It's the kind of estate Fabric makes possible.

Weaver also has a first-class command-line interface for build, load and test across the whole estate. AI agents already use it to develop and maintain I ❤️ Gov, running the full loop of change, run, check and fix without leaving the terminal.

The benefit isn't just fewer pipelines. It's using Fabric's full capability without solving the same engineering problems again and again.

Is dbt still a good choice?

Absolutely. If your main need is managing SQL transformations, dbt is mature and highly capable, and there's no reason to abandon a working architecture.

But if your work is spreading across engines, it's worth asking some harder questions.

How much effort goes into coordinating separate systems?

How often do you adapt your engineering to fit the framework?

Which Fabric capabilities are you avoiding because they're awkward to integrate?

And how much infrastructure have you quietly built around dbt just to make it all work?

Because at some point, the framework that helped you get started may become the thing constraining what you do next.

The question isn't whether dbt works on Fabric. It's whether we're letting Fabric become everything it could be.
