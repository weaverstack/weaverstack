How Weaver works

Your Warehouse query may depend on a Lakehouse table, and your Power BI model may need both. Write that work in familiar Python, SQL and Power BI files; Weaver deploys it and uses the dependencies to order your loads.

You define the data work. Weaver handles deployment, loading routines and the record of what ran.

Write code you already know

T-SQL

Write an ordinary SQL query. Add a comment that tells Weaver the table name, key and columns.

Warehouse/Curated/Parcel.Event.sql
/*
Table ID: Parcel.Event
Description: Parcel events.
Lineage: Example input.
Primary key: parcel_id
Schema:
  parcel_id: varchar(20)
*/
select 'P-1001' as parcel_id;

Python

Write a Python class with a read() method. Describe the table in the file and return a Spark DataFrame.

Tables/Parcel__Event.py
"""Table ID: Parcel.Event
Description: Parcel events.
Lineage: Example input.
Schema:
  parcel_id: string
"""
from weaver import Table

class Parcel__Event(Table):
    def read(self):
        return self.spark.createDataFrame(
            [("P-1001",)], "parcel_id string"
        )

TMDL

Add a standard TMDL annotation to apply modelling rules. Weaver leaves your original Power BI files unchanged.

Parcel.tmdl
model Model
    annotation 'Weaver.AutoHideForeignKeys' = true

Each file tells Weaver what it represents and what rules to follow.

File paths and naming conventions supply the rest of the structure.

How to write a Weaver project →

The catalogue

When a load fails, you need to know which definition ran, what finished and which consumers need attention. Weaver records those answers in its Catalogue: ordinary tables under the _ schema of a Fabric Warehouse. You can query them directly or explore them in the included Power BI Catalogue Dashboard, with no separate monitoring service to operate.

Build records your installed definitions and bindings here. Load and Test use that installed state and add their results; Health reads it to assess what is current, stale, failed or blocked. You can investigate a run without reconstructing it from console output.

Turn your source logic into repeatable loads

You write the query or Python method that supplies the data. Weaver builds the surrounding loading routines, then runs the installed work using the recorded dependency graph.

Order work across engines
When your Warehouse reads a Lakehouse table, Weaver orders the selected loads and waits for the required SQL endpoint refresh before running the reader.
Apply incremental changes
You choose the new, changed and deleted records each source supplies. Weaver stages and applies those changes, using bookmarks to track each consumer's progress.
Run independent work together
Your unrelated loads can run at the same time within configured concurrency limits, while consumers wait for their dependencies.
Keep failures actionable
Load records completed and failed work. Choose fault-tolerant loading when you want independent branches to continue after a failure.
Check the result you expect
Define Tests that compare expected and actual rows, or Assumptions that find rows breaking a rule. Use SQL for stored data and DAX for model calculations.
Reuse modelling rules
Apply shared rules and model-specific TMDL overlays during Build, so you can maintain conventions across models while keeping your original Power BI files unchanged.

Weaver infers dependencies from Python imports and supported T-SQL references; declare dependencies explicitly for Spark SQL. Select the producers and consumers you want to run: dependencies order that selection rather than automatically loading every upstream item.

When another team owns a producer, each team can keep its own workspace and catalogue. Supply the participating catalogues to coordinate selected Load and Test work across their recorded connections. Build stays within one workspace; shared execution does not require a shared deployment.

One set of commands

You use the same lifecycle commands for Lakehouse, Warehouse and semantic-model work. Weaver chooses the execution path for each item: Spark for Lakehouse work, T-SQL for Warehouse work and Power BI APIs for model deployment and refresh. You select what to operate on instead of writing a separate orchestration script for each engine.

  1. BuildDeploy definitions and loading code from your project files.
  2. LoadRun installed data work and refresh selected models.
  3. TestRun installed validations against the results.
  4. HealthRead recorded state to see what needs attention.

For example, after setting up your project with an existing Warehouse target named Curated, you can preview a change, deploy it, load the data and check the result:

From your configured project folder
weaver build --item Warehouse/Curated --dry-run
weaver build --item Warehouse/Curated
weaver load Warehouse/Curated
weaver test Warehouse/Curated
weaver health

Use the same sequence for a Lakehouse or semantic model. Build your Lakehouse and Warehouse sources first, then build models and Reports in a separate call. Load refreshes the models; Build deploys Reports and connects them to their models. Reports use their model's data, so they have no separate Load or Test step.

When you edit a query or validation, Build installs that change for the next Load or Test. Read Health afterwards to see which deployments, loads or validations still need attention. The development guide walks through an actual change and its results.

Mirror: develop against existing data without copying everything.

Wipe empties the selected data destinations, including unmanaged contents inside them. Review its target and catalogue reset scope before running it.

Same files. Different workspaces.

Keep Warehouse/Curated in your source files and map it to Curated_Dev in development or Curated in production. Run Build with the appropriate workspace configuration to deploy and record those bindings. Your data logic stays the same while you choose where it runs. Set up the model's data connections for each environment through the relevant Fabric setup.
