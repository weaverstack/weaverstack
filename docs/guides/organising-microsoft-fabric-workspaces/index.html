Organising Fabric workspaces for independent teams

Keep team ownership while coordinating shared data. An experiment across 50 Fabric workspaces explores how separate projects can participate in one operational run.

Ownership does not remove dependencies

If you lead a data team in a large organisation, you want business teams to own their Fabric workspaces and release their work without involving the central team in every change.

The difficulty is that their data still depends on work owned elsewhere. Finance might run its own Warehouse and schedule, but read a customer table maintained centrally. When that table fails, Finance needs to understand which of its tables depend on it, and the central team needs to coordinate the repair.

This experiment used 50 real Fabric workspaces and separately configured projects to represent central and business teams. It tested whether the dependencies and run results already recorded by those projects could support both local recovery and a coordinated run.

1. Self-service data and the coordination problem

A common way to organise Microsoft Fabric workspaces for self-service data looks like this:

  • A central team owns the Bronze Lakehouse in one workspace.
  • Another team owns the Silver Lakehouse and Gold Warehouse in a second.
  • Shared semantic models live in a third.
  • Forty or fifty business areas own workspaces of their own. They read central data and occasionally one another's.

You can coordinate loads through a central scheduler or let teams manage their own schedules. In either case, someone still needs to understand the dependencies between teams and decide what to rerun after a failure. A successful load alone does not tell you whether its upstream data is current.

An enterprise needs the advantages of both. Each team should be able to operate on its own, while the organisation can still see its dependencies, assess the impact of a failure and coordinate recovery when necessary.

2. What Fabric already provides

Two properties of Fabric make an organisation-wide dependency graph possible without moving any data or adding a central service.

2.1 Qualify the object you mean

A name such as CustomerSales needs context. In this example, the workspace, item type, item name, schema and object name tell a reader which Warehouse table is being discussed. Folders use paths rather than Warehouse schemas; a model or Report is an item in its own right.

Display names help people locate the work; they are not immutable tenant-wide identifiers. Weaver matches installed items using their recorded Fabric IDs and uses the shortcut's source path to identify the table being read.

2.2 OneLake shares data across workspaces

Every Fabric tenant comes with a single OneLake instance (Microsoft 2026a). Its shortcuts let an item in one workspace read data held by an item in another, including a Lakehouse reading a Warehouse, without copying it (Microsoft 2026b).

In this experiment, Spark addressed tables in other workspaces directly by four-part name. A Warehouse's T-SQL reached only items in its own workspace, so each business team brought central Gold tables into its workspace through shortcuts in a small bridge Lakehouse and read them through that Lakehouse's SQL analytics endpoint.

Fabric also supplies item lineage and impact analysis, including downstream items in other workspaces. The question here is more specific: how do the managed tables and loads depend on one another, which recorded operations need attention, and what should run next?

3. The two missing pieces

Beyond what Fabric provides, an organisation-wide dependency graph needs two pieces of information about each object.

3.1 Connect the recorded dependencies

Finance's shortcut already identifies the central item and path it reads. Given both catalogues, Weaver matches that source to the central team's installed table and connects the recorded dependencies. The teams do not need to maintain the same connection again in a second map.

3.2 Follow the load results

Each object must also record its operational state: when it last loaded, whether that load succeeded, and when its upstream last changed. With that, a failed table can be traced to every object that read it, and an object that loaded successfully before its upstream was repaired can be identified as behind.

Each team can keep these records in its own catalogue. A caller with access supplies the participating catalogues to assemble the graph needed for an investigation or selected run. Weaver follows those records; it does not discover every workspace in the tenant automatically.

3.3 A bonus: concurrency

Concurrency is not required for the graph, but the graph makes it available: once the dependencies are known, loading across workspaces becomes a scheduling problem. Independent branches in different workspaces should run together, while each reader waits only for its own upstream, including the SQL analytics endpoint refresh or OneLake publication between them. The techniques are the same as within one estate, described in Performance Engineering on Microsoft Fabric.

5. The implementation: Weaver

Weaver is an open-source data engineering framework for Microsoft Fabric. In this setup, each project keeps a catalogue in a Fabric Warehouse. Build records the managed objects and dependencies; Load and Test record their results. Those records let a caller investigate connected work without moving the teams into one project.

5.1 The Weaver CLI

Give Health the catalogues needed to follow the connection. For Load and Test, supply the same context and select the items or workspaces to run. Repeating --catalogue alone does not select every team's work: without item selection, the working workspace's catalogue sets the default scope.

Terminal: three participating catalogues
# Assess these catalogues and their recorded connections
$ weaver health --workspace SPREAD_TEAM_05 \
  --catalogue SPREAD_TEAM_05/Warehouse/Catalogue \
  --catalogue SPREAD_BRONZE/Warehouse/Catalogue \
  --catalogue SPREAD_CENTRAL/Warehouse/Catalogue

# Team 05 reloads only what is behind, reading its upstream for context
$ weaver load SPREAD_TEAM_05 --workspace SPREAD_TEAM_05 --stale \
  --catalogue SPREAD_TEAM_05/Warehouse/Catalogue \
  --catalogue SPREAD_BRONZE/Warehouse/Catalogue \
  --catalogue SPREAD_CENTRAL/Warehouse/Catalogue

These are complete commands for three catalogues, not abbreviated commands for all 50. Health follows recorded ancestry through the supplied catalogues and reports unavailable or unassessable context as incomplete. A selected load runs as one graph under one workflow ID; each object runs in its owning workspace and its result stays in that team's catalogue.

Give the running identity read access to each catalogue you include. To load another team's objects, it also needs permission to run that work and record the results there. See the permissions reference for the command requirements.

5.2 The Catalogue Dashboard

Use the Catalogue Dashboard to explore the participating catalogues in Power BI. Start with Workspaces to see the connections, then use Health and Orchestration to investigate a failure. Filters narrow the pages by workspace, item and object.

The Dashboard reads up to ten catalogues over Direct Lake; Import mode supports more than ten and needs refreshes to pick up new records. It does not write to the catalogues. Exported HTML is a snapshot of the deployed model's data, and a downloaded local copy opens without a running Fabric capacity.

6. Results

The deliberate failure in BRZ.Customer raises three practical questions: which recorded downstream work depends on it, what must the central team repair, and what should a business team reload afterwards? 6.1 Knowing the impact of a failure

The impact check found 61 downstream Warehouse tables, five Lakehouse tables and 11 semantic models with findings linked to the failed load. These are managed loadable objects, not a count of every business or end-user impact. The central team and downstream owners could use the same recorded cause rather than reconstructing the connection from separate pipeline histories.

A load-state finding does not establish what every report user sees or whether the business calculation is correct. Thin-report workspaces have no separate data load to select here, but their reports can still display affected source data.

6.2 Each team recovers on its own terms

The central recovery selected work across Bronze, Silver/Gold and the shared semantic model, leaving the business teams' loads unselected. Weaver ordered that work and waited for the publications and endpoint refreshes its readers needed.

After the central repair, Team 05 checked its position, reloaded its two stale tables and returned to green. The command above shows that selected scope while using the central catalogues for context. Its project and schedule remained its own; it did not have to run every other business team's pipeline to recover.

6.3 Teams that read one another's data

Teams 01 and 02 read each other's summaries. Weaver reports the cycle and orders its members deterministically, running each selected member once per invocation. Dependencies that close the cycle can therefore read results left by an earlier run; this is not an iteration until the teams' results converge.

Health suppresses relative newer-load comparisons within a cycle. It still reports and propagates relevant failed, Pending and overdue states, so a cycle does not hide a failed load.

6.4 Coordination when the organisation needs it

For a wider recovery, a caller supplies the participating catalogues and selects the workspaces or items to rerun. --stale narrows that selection to work whose recorded state requires another load.

The coordinated timing in the table includes catalogue reads, graph planning, the Spark wait, execution and recording. It describes this small-data estate and trial capacity, not a performance guarantee for another workload. The invocation coordinated the run; it needed no permanent central scheduling service or shared project.

7. Team ownership, coordinated operation

The experiment shows a practical way to keep team ownership while coordinating work across Fabric workspaces. Each simulated team kept its own project and catalogue; the wider run used the dependencies those projects already recorded.

  1. Central coordination.A central data team can use the participating catalogues to assess dependencies and coordinate selected work across workspaces.
  2. Business-team ownership.A business team can keep its own project and schedule, check its upstream dependencies and recover its affected work after the upstream repair.

Both ways of operating use the same catalogue records. Teams do not need to move into one centrally managed project or maintain a second cross-team dependency map.
